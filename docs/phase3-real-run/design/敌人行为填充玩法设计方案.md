# 敌人战斗表现与行为填充设计方案

给 AutoUE PuerTS 生成流水线补敌人的"打起来的手感"：跨帧攻击生命周期、可见表现、行为模式选择。写给接着做这块的工程师看——敌人已经能刷、能追、能碰到人扣血，现在缺的是"看得见的前摇、能躲的攻击、不同怪打法不一样"。

> **代码基线（2026-07-01 核对）**：spawn→感知→移动→近战碰撞→受伤→死亡→通关的闭环已在 PIE 跑通并验收（`EncounterRuntimePIE验收记录-20260630.md`）。碰撞查询、模块驱动装配、冰陷阱解耦都已落地。本方案只在这个能跑的闭环上补战斗质感，不重做生成链。

## 缺口结论（三个真问题，按优先级）

**P1（玩家能感知到的核心手感）——攻击是单帧瞬时的。** `enemy_combat.ts.tmpl:8` 的 `resolveMeleeHit` 在一次 `tick` 里把 Telegraphing→Attacking→resolveMelee→Recovering 全走完。玩家看不到前摇、没有可躲窗口，攻击"一瞬间就结算完了"。→ 改成**跨帧相位状态机**。

**P1（否则永远是隐形攻击）——没有表现层。** 前摇 / 命中 / 死亡目前只有 `log(...)`，PIE 里敌人挥手没有任何视觉。→ 新增 **`EnemyPresentationRuntime`**，且必须挂进模块驱动装配才能被生成出来。

**P2（不同怪打法一样）——没有"行为模式"抽象。** `enemy_brain.ts.tmpl:10-35` 现在是"把该敌人所有 combat/movement 能力每帧全 dispatch 一遍"，无法表达"僵尸贴脸 vs 弓手拉开"的策略差异。→ 加 **behavior pattern 层**。

新攻击类型（area_burst / charge / combo）是 P5 后期，需要动支持矩阵，本期不做。

## 一、四层模型与落点

四层各自的职责、当前状态、以及"靠什么生成出来"（凡新增字段/模块都标明进入流水线哪个环节，否则视为没落地）：

| 层 | 职责 | 状态 | 生成落点 |
|---|---|---|---|
| Entity 实体 | 数值 / 资产参数 | ✅ | `data/libraries/dead_cells/entities.json` 的 `capability_bindings.params` |
| Behavior Pattern 行为模式 | 决策组织：选哪种移动+攻击 | ❌ | behavior 的 `runtime_params.pattern` + `EnemyBrain` 按 pattern 分派 |
| Attack Type 攻击类型 | 如何命中 + 生命周期 | ⚠️ 命中真了、生命周期是单帧 | 支持矩阵 `enemy.attack.*` + `EnemyCombat` 相位机 |
| Presentation 表现 | 前摇 / 命中 / 死亡的可见反馈 | ❌ | 新模块 `enemy_presentation` + 装配注册 + 事件钩子 |

关键约束：所有新增的字段最终都要经 `behavior_spec.py` 的 `resolve_behavior_capabilities` 展开进 `resolved_capabilities[].params`，再随 `behavior_spec_json` 下发到运行时。**这条路已经通，加字段不用改渲染器。**

## 二、攻击生命周期：单帧改跨帧相位机（本方案核心）

> 现方案：`resolveMeleeHit` 一帧内 Telegraph→Attack→Resolve 全做完——代价是前摇为 0、玩家无法躲、攻击不可读。
> 新方案：敌人记录上挂一个按 `now` 推进的相位子状态，前摇 / 命中窗口 / 后摇跨多帧展开，命中只在 active 窗口内做一次。

### 2.1 敌人记录扩展

在 `enemy_registry.ts.tmpl:2-3` 的 `AutoUEEnemyRecord` 上新增独立的 `attack` 子状态，**不改现有 `state` 字段**（移动状态机已验收，避免连带回归）：

```ts
// enemy_registry.ts.tmpl  AutoUEEnemyRecord 新增字段
attack?: {
  type: string;        // 'melee_hitbox' | 'projectile_spawn' | 'self_destruct'
  phase: 'idle' | 'windup' | 'active' | 'recover' | 'cooldown';
  phaseUntil: number;  // 绝对秒，和 now 比较
  hitApplied: boolean; // active 窗口内是否已结算，防一次攻击多次命中
};
```

### 2.2 相位推进

由 `enemy_brain.ts.tmpl` 的 `tick(now, dt)` 驱动，攻击执行下沉到 `EnemyCombat.advance(enemy, target, now)`：

```
[idle]     目标进入 attack_range 且 cooldown 就绪  ──▶ [windup]   phaseUntil=now+windup_seconds   【Presentation.telegraph】
[windup]   到期                                    ──▶ [active]   phaseUntil=now+active_seconds    【Presentation.showHitbox】
[active]   期间且 !hitApplied                       ──▶ 命中查询 resolveMelee / overlapActors
                                                        命中→applyDamage + hitApplied=true         【Presentation.impact】
[active]   到期                                    ──▶ [recover]  phaseUntil=now+recover_seconds
[recover]  到期                                    ──▶ [cooldown] phaseUntil=now+cooldown_seconds
[cooldown] 到期                                    ──▶ [idle]
```

- `resolveMeleeHit` 拆成 `beginAttack()`（进 windup）+ `advance(now)`（推进相位、active 窗口内做命中）。已实现的 `resolveMelee` 挪到 active 分支，不重写。
- `projectile_spawn`：windup→active 边界 spawn 一次投射物，命中由投射物自身 overlap 结算（不在 active 窗口做距离判定）。
- `self_destruct`：active 边界做一次 `overlapActors(敌人位置, explode_radius)` 群伤，随后 `emitDeath`。

### 2.3 新增能力参数

进对应 `enemy.attack.*` 能力的参数定义（`abilities.json` 的 `params_schema`）+ 各敌人 `entities.json` 缺省：

| 参数 | 用途 | 默认 |
|---|---|---|
| `windup_seconds` | 前摇（可躲窗口） | 0.35 |
| `active_seconds` | 命中窗口 | 0.12 |
| `recover_seconds` | 后摇 | 0.45 |
| `cooldown_seconds` | 冷却（沿用现有 `cooldown`） | 1.2 |
| `hitbox_radius` | 命中球半径 | 110 |
| `explode_radius` | 自爆半径 | 220 |

⚠️ 待验证假设：`active_seconds=0.12` 在 PIE 帧率下是否够稳定命中一帧——需实测，太短可能因抖动漏帧，太长会一次前摇打多下。以 01-zombie 首跑校准。

## 三、表现层 `EnemyPresentationRuntime`（占位方案，先跑通）

本期表现用**零依赖占位**：动态材质变色 + 临时球/盒 + 相机震动。不接 Niagara / 不等美术资产，目的是让 PIE 里"看得见在打"。

### 3.1 接口（最小版）

```ts
// enemy_presentation_runtime.ts.tmpl  占位表现接口
telegraph(enemy, attackType, params)  // 前摇：敌人材质变红 + 可选攻击范围提示球
showHitbox(enemy, params)             // active：临时半透明球/盒显示命中体，窗口结束销毁
impact(target, params)                // 命中：目标闪白 + 轻击退
projectileFx(enemy, params)           // 发射：muzzle 占位球
explosion(enemy, params)              // 自爆：放大球体 + 相机震动
death(enemy, params)                  // 死亡：变灰/缩小后 destroyActor
```

占位实现全部复用现有底层，不引新依赖：
- 变色：复用 `behavior_orchestrator` 里的动态材质模式（`makeMaterial` → `SetVectorParameterValue('Color', ...)`），本期抽成 `WorldAdapter` 公用方法。
- 临时体：`makeWorldMesh` + `NoCollision` + `WorldAdapter.bindTimer` 定时 `destroyActor`。
- 相机震动：`behavior_orchestrator` 已有的相机通道，抽成 `WorldAdapter.cameraImpulse` 复用。

### 3.2 装配落点（不注册就生成不出来）

```python
# typescript_runtime_template_plan.py  在 TEMPLATE_BY_MODULE 里加一行
TEMPLATE_BY_MODULE["enemy_presentation"] = (
    "enemy_presentation_runtime",
    "TypeScript/content/generated/AutoUEEnemyPresentationRuntime.ts",
    "createAutoUEEnemyPresentationRuntime",
    "AutoUEEnemyPresentationRuntimeContext",
)
```

配套四步：
1. 新建模板 `templates/typescript/enemy_presentation_runtime.ts.tmpl`。
2. `runtime_support_matrix.py`：给所有 supported 的 `enemy_attack` / `enemy_health` / `enemy_death` 条目的 `required_runtime_modules` 加 `"enemy_presentation"`——只要有敌人攻击就自动带上表现层。
3. `behavior_orchestrator.ts.tmpl:55-88` 的 `runtimeServices` enemy 分支：`generatedFactory('./AutoUEEnemyPresentationRuntime', ...)`，注入 `enemyCombat` / `enemyHealth` / `enemyDeathEvents`。
4. 相位机各阶段调对应 `presentation.*`（telegraph/showHitbox/impact/death）。

走的是既有"模块→模板→装配"链，不碰渲染器，不破坏已验收流程。

## 四、行为模式类型：给 `EnemyBrain` 加策略选择

把 `enemy_brain.ts.tmpl:10-35` 从"每帧全 dispatch"改成"按 pattern 分派"。behavior 携带 `runtime_params.pattern`，Brain 用一张表决定"本帧怎么移动 + 是否发起攻击"：

| pattern | 移动 | 攻击触发 | 组合能力 |
|---|---|---|---|
| `fast_chase_and_melee` | chase_target | dist ≤ attack_range | detect + chase + melee_hitbox |
| `heavy_chase_and_melee` | chase_target（慢） | dist ≤ attack_range | detect + chase + melee_hitbox（高伤/长前摇） |
| `keep_distance_and_projectile` | keep_distance | dist ≤ detect_range 且冷却就绪 | detect + keep_distance + projectile_spawn |
| `chase_and_self_destruct` | chase_target（高速） | dist ≤ explode_radius | detect + chase + self_destruct |
| `shield_chase_counter` | chase_target | 受击时格挡；近身近战 | detect + chase + directional_block + melee_hitbox |

落点：
- `pattern` 走 behavior 的 `runtime_params.pattern`，随 `behavior_spec_json` 下发，纯运行时消费，不加流水线新字段。
- `EnemyBrain` 用 `PATTERN_TABLE`（移动函数 + 攻击判定谓词）替代当前遍历。
- ⚠️ **未识别 pattern 时回退到当前"全 dispatch"行为**——保证 01～04 已验收用例不回归。

## 五、攻击类型四件套清单

每种攻击类型要能生成，四件必须齐（缺一即"设计没落地"）：**① 支持矩阵条目 ② `EnemyCombat` handler ③ 能力参数定义 ④ 表现钩子**。

| 攻击类型 | ① 矩阵 | ② handler | ③ 参数 | ④ 表现 | 本期? |
|---|---|---|---|---|---|
| `melee_hitbox` | ✅ supported | ⚠️ 改相位机 | + windup/active/recover/hitbox_radius | telegraph+showHitbox+impact | ✅ |
| `projectile_spawn` | ✅ supported | ⚠️ 补方向/速度/命中回调 | projectile_class_path/speed | projectileFx+impact | ✅ |
| `self_destruct` | ✅ supported | ⚠️ 前摇+overlap 群伤 | explode_radius/windup | telegraph+explosion+death | ✅ |
| `directional_block` | ✅ supported | ⚠️ 真格挡（按受击方向减免） | block_angle_degrees | 格挡态材质/火花 | ✅ |
| `area_burst` | ❌ `runtime_support_matrix.py:149` supported=False | ❌ 新增 | radius/delay | 地面提示圈+延迟爆 | ❌ 后续 |
| `charge_attack` | ❌ 无条目 | ❌ 新增（冲刺+sweep） | charge_speed/duration | 冲锋残影 | ❌ 后续 |
| `combo_melee` | ❌ 无条目 | ❌ 多段 hit window | combo_steps[] | 逐段 telegraph | ❌ 后续 |

前 4 种在既有 supported 集内，是本期目标。后 3 种要改矩阵（`supported=False`→真 + 加 canonical capability id 到 `CANONICAL_ENEMY_CAPABILITY_IDS`），列为后期。

⚠️ 防"全有或全无"：某敌人若选了尚未实现的攻击类型，应走 `blocked_behaviors` 降级、渲染其余，而非整份 abort。落地前先确认 `typescript_runtime_template_plan.py:79` 附近的 unsupported 处理现状（上一轮是否已改降级）。

## 九、修复当前主链路的行动方案

当前主链路要从“repo 级 fixture 能生成”修到“真实 `autoue.py run` 能稳定生成敌人并进 PIE”，按下面顺序处理。

### 9.1 修正敌人输入入口

问题：`scripted_smoke` 仍固定输出 `freeze_trap` 和空 `encounters`，不能作为敌人主链路 smoke。

行动：

1. 保留现有 `scripted_smoke` 给 freeze trap 冒烟，不改其语义。
2. 新增一个敌人专用 profile 或 fixture 注入入口，例如 `scripted_enemy_zombie` / `scripted_enemy_archer` / `scripted_enemy_kamikaze` / `scripted_enemy_shield`。
3. 这个入口只固定节点 1-5 的选择与 encounter 输入，不写死节点 6-10 的 codegen 输出；后续模板仍由确定性节点实时渲染。
4. 每个 profile 输出后先校验：
   - `entity_behavior.selected_entity_ids` 是目标敌人；
   - `behavior_spec.resolved_capabilities[].params` 含攻击相位参数；
   - `encounter_spec.encounters` 非空。

### 9.2 修正 CLI / wrapper 的真实调用方式

问题：旧说明里的 `--prompt` / `--out` 不存在，直接照抄会跑不起来。

行动：

1. wrapper 统一创建临时目录：
   - `<tmp>/input/001.txt`
   - `<tmp>/output`
2. 调用：

```powershell
python autoue.py run --input-dir <tmp>/input --output-dir <tmp>/output --llm-profile <profile>
```

3. 从 `<tmp>/output/demo_001` 读取 bundle、stage report、TypeScript 产物和后续验证证据。

### 9.3 固化 scene spawn manifest 口径

问题：fixture manifest 只能让 planner 过；PIE 真生成必须依赖地图里真实 spawn point。

行动：

1. 默认用 `config/local.json.scene_spawn_manifest.enabled=true` 导出真实 manifest。
2. 只在离线测试时允许 `allow_fixture=true`。
3. wrapper 在进入 PIE 前断言：
   - manifest 中存在目标 `spawn_group`；
   - encounter 的 `spawn_group` 能在 manifest 中匹配；
   - `allowed_enemy_tags` / spawn point tags 不阻断当前敌人。

### 9.4 补强 AIDev stale 防线

问题：staging 已清旧 TS 并 tsc，但不负责 TypeScript Blueprint 初次创建，也未确认 PuerTS 是否还有额外 JS 缓存。

行动：

1. wrapper 在 stage 后检查 AIDev 侧：
   - `TypeScript/AutoUEGeneratedGameModeAdapter.ts`
   - `TypeScript/AutoUEGeneratedCharacterAdapter.ts`
   - `Content/Blueprints/TypeScript/AutoUEGeneratedGameModeAdapter.uasset`
   - `Content/Blueprints/TypeScript/AutoUEGeneratedCharacterAdapter.uasset`
   - `DefaultEngine.ini` 的 `GlobalDefaultGameMode`
2. 首次搭建缺 uasset 时，调用现有 TypeScript Blueprint 创建路径；不能把“tsc 过了”当成 PIE 可运行。
3. 做一次 windup 探针：把 `windup_seconds` 改成明显值（如 1.5），确认 `Telegraph→Active` 间隔同步变化；若不变，再追 PuerTS JS 缓存。

### 9.5 补强 PIE validator

问题：当前 PIE validator 的 pass 只要求 `enemy_count>0`，过浅。

行动：

1. 保留 `run_autoue_pie_validation.py` 的结构性检查：PIE world、GameMode、Pawn、enemy_count。
2. 新增 wrapper 级日志 gate：
   - 通用相位链；
   - case-specific 攻击类型；
   - 禁止 `RuntimeModuleUnavailable`、`SpawnPointMissing`、非忽略 Puerts Error。
3. 后续再把这组 gate 合入 `validate_autoue_runtime_log.py`，让它支持 `--require-enemy-attack-phase` 和 `--case archer|...`。

### 9.6 最小完成顺序

1. 先落 `regen_enemy_pie.py --mode fixture --case zombie`，证明方案 B 热迭代闭环。
2. 扩到 `archer/kamikaze/shield`，补齐 case-specific 日志 gate。
3. 再做 `scripted_enemy_*` profile，让主链路从节点 1-10 也能稳定生成指定敌人。
4. 最后跑真实 LLM prompt，只把它作为端到端产品验收，不作为模板开发内循环。

完成口径：

- 方案 B：四个 case 均能一键 stage、tsc、PIE，并通过相位链日志断言。
- 主链路：不用手改 bundle，`autoue.py run --input-dir ... --output-dir ... --llm-profile scripted_enemy_<case>` 能生成目标敌人、部署进 AIDev、PIE 中出现目标攻击类型日志。
